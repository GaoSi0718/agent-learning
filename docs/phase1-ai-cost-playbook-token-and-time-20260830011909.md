# AI 资源消耗图鉴：什么最烧 Token、最花时间（初学者版）

> **面向对象**：AI 初学者 · Agent 学习路线 W1–W6
> **配套脚本**：`w6_cost_lab.py`（放在项目根目录，离线可跑，零 API 成本）
> **生成日期**：2026-08-30
> **阅读方式**：第 0 节给结论；第 1–2 节建立心智模型；第 3–5 节是"避坑清单"；第 6 节是动手实验（**强烈建议至少跑实验 1/2/3**）；第 7–9 节是速查与答疑。

---

## 0. 先给结论

1. **最烧钱的是"上下文滚雪球"**——第 N 轮的输入 = 前 N-1 轮的全部历史。你以为只问了一句话，实际上是在为这几十轮的旧内容重新买单，总消耗随轮次**平方增长**。
2. **第二大坑是"工具结果回灌"**——一次网页抓取、一次日志读取的内容进了上下文，后面**每一轮**都要为它再付一次钱。
3. **第三是"长输出 + 反复重试"**——输出 token 单价通常是输入的 4–5 倍；而一个跑偏的 Agent 循环，前 8 次失败的 token 全部沉没。
4. **时间和 token 是两回事**——图片输入"烧钱不花时间"，图像生成"不烧钱但很慢"。混为一谈会让你优化错方向。
5. **RAG（检索）存在的全部理由就是省钱**——你的 W6 项目用 BM25 只取 top-k 片段，本质就是在对抗上面第 1、2 条。

> **如果只记一句话**：Token 不是按"你说了多少"计费，而是按"模型每次要读多少"计费。所以**减少上下文、缩短输出、少让它重来**，比任何其他技巧都管用。

## 1. 三个必须先懂的概念

### 1.1 Token 到底是什么

Token 不是"字"，也不是"词"，是模型切分文本的最小单位。经验量级（**不同 tokenizer 差异很大，务必自己实测**）：

| 内容 | 经验换算 | 备注 |
|---|---|---|
| 中文 | 1 个汉字 ≈ 0.7–1.5 token | 常用字偏少，生僻字可能 1 字 2–3 token |
| 英文 | 1 token ≈ 4 个字符 ≈ 0.75 个单词 | "unbelievable" 可能被切成 3 段 |
| 代码 | 1 行 ≈ 10–20 token | 缩进和符号也占 token |
| 数字/标点 | 每个符号都可能单独成 token | JSON 的大括号、引号都算钱 |

**为什么这很重要**：你写"请帮我总结一下这份员工手册"，这句话本身只有十几个 token，几乎不值钱。真正花钱的是你塞给它的那份手册。

### 1.2 三类资源，别混为一谈

| 资源 | 本质 | 你感受到的 | 优化方向 |
|---|---|---|---|
| **Token** | 钱 | 账单 / 额度消耗 | 缩短输入和输出 |
| **时间** | 等待 | 转圈圈、进度条 | 并行化、减少往返 |
| **上下文窗口** | 容量 | "装不下了"、被自动压缩 | 控制单轮体积 |

一个任务的"贵"，可能贵在钱（token），也可能贵在等待（时间），或者两者都贵。**先判断是哪一类，再选优化手段**，否则容易白费力气。

### 1.3 核心心智模型：每轮都要为整个上下文重新付费

这是最重要的一节。模型是**无状态**的——它不"记得"上一轮，所谓的记忆，是客户端把历史对话**重新拼进 prompt 再发一遍**。

```
第 1 轮发送：[问题1]                      → 付费 2000 token
第 2 轮发送：[问题1][回答1][问题2]          → 付费 4000 token
第 3 轮发送：[问题1][回答1][问题2][回答2][问题3] → 付费 6000 token
...
第 20 轮发送：前 19 轮全部 + 问题20        → 付费 40000 token
```

**一次对话的总消耗 = 各轮消耗之和 ≈ 每轮新增 × N²/2**，这就是为什么聊得越久越贵，而且是加速变贵。

## 2. 全景定位图

把常见事务按「token 消耗」和「时间消耗」两个维度摆开，会得到四个象限：

```
                    时间消耗 高 ↑
                         │
   图像/视频生成 ●        │      ● 网页抓取结果回灌
   人工审批/等待 ●        │        ● 批量嵌入/索引
   编译/跑测试   ●        │          ● Agent 循环/重试
                         │
  ───────────────────────┼───────────────────────→ token 消耗 高
                         │
   简单问答/分类 ●        │      ● 代码库级检索
                         │        ● 长文本输出
                         │          ● 图片/截图输入
                         │
```

**两个反直觉的点，值得单独记住**：

- **图片输入在右下角**：一张 1080p 截图 ≈ 1000–2000 token，钱花得肉疼，但它不花时间，一次调用就完了。
- **图像/视频生成在左上角**：token 几乎不要钱（你只发一句提示词），但每次要等几十秒到几分钟——**它贵在时间，不贵在 token**。

所以"我这个任务很贵"这句话要拆开说：是账单贵，还是等得久。

## 3. 吃 Token 的九大事务

下面每条都给出：**原理 → 在 WorkBuddy 里的真实例子 → 量级 → 怎么省**。

### 3.1 多轮长对话（滚雪球）★最狠

- **原理**：上下文累积，每轮重付全量历史（见 1.3 节）。
- **在 WorkBuddy 里长什么样**：早上开一个会话让它改 W6 的代码，聊到晚上还在同一个会话里问"再帮我加个功能"。第 30 轮时，每问一句都在为前面 29 轮的对话、代码、报错日志付费。
- **量级**：每轮若新增 2000 token，聊 20 轮累计约 **42 万 token**；聊 40 轮约 **164 万**（四倍轮次，四倍多的费用——因为是平方增长）。
- **怎么省**：
  - 一个任务完成后**开新会话**，别一条道聊到黑。
  - 需要长期记忆时，让 AI 把结论**压缩成一段摘要**，贴进新会话（几百 token 换掉几万 token）。
  - 关注界面上的上下文占用提示（多数 AI 编程工具会在状态栏显示占用比例，接近上限时会提示压缩或自动压缩——**具体以你当前版本的界面为准**）。

### 3.2 工具结果回灌

- **原理**：工具（搜索、读文件、跑命令）的输出会进上下文，之后每轮都为它付费。
- **在 WorkBuddy 里长什么样**：让它"搜一下 New API 的部署方法并总结"，它抓回 5 个网页的全文，几万 token 一次性进上下文。后面你再问任何问题，这几万 token 都要跟着走一遍。
- **量级**：一次网页全文抓取 ≈ 5k–20k token；一个 5MB 的日志文件能轻松吃掉几万 token。
- **怎么省**：
  - 让 AI 抓完就**立刻摘要**，并明确说"只保留结论，丢弃原文"。
  - 命令输出一律截断：`git log -p | head -50`、`pytest -x --tb=short`。
  - 该开新会话时就开——新会话是清掉垃圾上下文最干净的方式。

### 3.3 Agent 循环 / 反复改 bug

- **原理**：Agent 每迭代一次，就是把完整历史（含上一次的错误和你的反馈）再发一遍。
- **在 WorkBuddy 里长什么样**：让它"把这个报错修一下"，它改了 8 次还没改对。前 7 次的尝试、报错、你的"还是不行"全部堆在上下文里，第 8 次调用贵得离谱。
- **量级**：一次任务迭代 10–50 次很常见。若平均上下文 3 万 token，跑 20 次就是 60 万 token。
- **怎么省**：
  - **失败 2–3 次就停手**，换个更精确的描述重开一个干净会话，比继续纠缠便宜得多。
  - 报错信息要**给全但给准**：贴关键 traceback 的前 30 行，而不是整个终端滚动记录。
  - 给 Agent 设定明确的最大尝试次数（若工具支持）。

### 3.4 长文本输出

- **原理**：输出 token 单价通常是输入的 **4–5 倍**，且输出是逐 token 串行生成的，无法并行。
- **在 WorkBuddy 里长什么样**："帮我把整个项目的使用说明写出来""生成一份 5000 字的调研报告"。钱和时间的双重消耗。
- **量级**：输出速度约 20–60 token/秒。5000 字中文报告 ≈ 6000+ token ≈ 等 2–5 分钟。
- **怎么省**：
  - 让它**先列大纲**，确认后再分段生成。
  - 明确要求"简洁""控制在 XXX 字以内"。
  - 能用模板填充的，别让模型自由发挥。

### 3.5 推理 / 思考型模型

- **原理**：带"深度思考""reasoning"能力的模型，会在内部生成大量思考 token，**这些 token 你没看到，但账单上有**。
- **在 WorkBuddy 里长什么样**：选了带推理的模型后，同一个问题返回的 `reasoning_tokens` 可能是正文的几倍。
- **量级**：思考 token 常占总消耗的 30%–70%。
- **怎么省**：
  - 简单任务（格式转换、摘要、分类）**关掉推理**或用小模型。
  - 复杂推理任务（多步规划、数学、代码架构）才开。

### 3.6 大文件整篇塞上下文

- **原理**：不做检索，直接把整份文档当输入。
- **在 WorkBuddy 里长什么样**："这是我们公司 80 页的 HR 制度手册，帮我回答员工问题"——然后每次提问都带着整本手册。
- **量级**：一页纯文本 PDF ≈ 500–1000 token；80 页手册 ≈ 4–8 万 token。**问 50 个问题 = 付费 50 次整本手册**。
- **怎么省**：这正是 RAG 要解决的问题——**检索 top-k 片段，只带必要内容**（见实验 3）。

### 3.7 图片 / 截图输入

- **原理**：视觉模型按切块（tile）计费，图片越大切得越多。
- **在 WorkBuddy 里长什么样**：截一张全屏 UI 图丢进去问"这个按钮为什么点不动"。
- **量级**：1080p 截图 ≈ 1000–2000 token；4K 大图可能翻倍。
- **怎么省**：
  - **先缩放到 512–768px 宽度**再上传，通常答案没差别，token 却能降到 1/3。
  - 只截关键区域，别整屏截。
  - 能贴文本就别贴图（报错日志贴文字比截图便宜得多）。

### 3.8 批量嵌入 / 索引

- **原理**：向量化整个文档库需要把所有文本过一遍 embedding 模型。
- **在 WorkBuddy 里长什么样**：搭建知识库时反复全量重建索引。
- **量级**：与文档总量成正比；每次全量重建 = 全库重算一遍。
- **怎么省**：**增量更新**——只对新文档/修改过的文档重新嵌入。索引做好后存本地，别每次启动都重建。

### 3.9 缓存未命中

- **原理**：很多 API 提供"提示词缓存"——相同前缀的内容第二次调用只收很少的钱（常见是 1 折左右）。但缓存是**按前缀匹配**的，改一个字，后面全部失效。
- **在 WorkBuddy 里长什么样**：系统提示词、项目说明、固定材料每轮都被重新发送。如果你每次都微调开头几个字，缓存永远命中不了。
- **量级**：命中 vs 未命中，可能差 5–10 倍单价。
- **怎么省**：**把稳定内容放最前面，把易变内容（时间戳、当前问题）放最后**。这是最容易被忽略、收益又很高的一条。

## 4. 吃时间的八大事务

| 事务 | 在 WorkBuddy 里的真实例子 | 为什么慢 | 怎么省 |
|---|---|---|---|
| **串行工具链** | 让它依次读 10 个文件、跑 5 条命令，一条一条来 | 每一步都是一次完整往返，时间累加 | 明确的独立任务要求它**并发执行** |
| **长输出生成** | 让它写一份完整项目文档 | 输出逐 token 串行，5000 字要等几分钟 | 分段生成、先大纲后正文 |
| **图像/视频生成** | 让它生成一张配图 | 排队 + 计算，几十秒到几分钟不等 | 批量提交而非逐个等待；接受等待 |
| **网页抓取/渲染** | 让它查某个需要 JS 渲染的网页 | 渲染、反爬、超时重试 | 优先用有 API 的数据源；设置超时 |
| **编译/构建/测试** | 让它跑 `pytest`、`npm install` | 与模型无关，但计入你的等待 | 缩小测试范围、用增量构建 |
| **大文件上传/解析** | 上传一本带扫描图的 PDF | 解析 + OCR 按页数线性增长 | 先提取纯文本层，避免无谓 OCR |
| **人工审批/确认** | 工具弹出"是否执行此命令"等你点 | 人类响应速度就是天花板 | 可信操作设为自动批准（注意安全边界） |
| **限流退避重试** | 并发高时突然整体变慢 | 触发速率限制，指数退避等待 | 控制并发数、错峰、用批处理接口 |

> 注意最后两行：**"等"不一定是在算，也可能是在排队或被限流**。任务突然整体变慢时，先怀疑限流而不是模型。

## 5. 三个"非线性"暗坑

之所以叫暗坑，是因为它们的代价**不是线性增长**，而是会在某个点突然爆炸。

### 5.1 缓存失效的悬崖

缓存按前缀匹配。假设你的 prompt 结构是：

```
[系统提示 5000 token][项目说明 20000 token][当前问题 200 token]
                                              ↑ 只有这里在变
```

这样前 25000 token 每轮都能命中缓存，只花 1 折的钱。但如果你的系统提示里**嵌入了当前时间戳**（比如"今天是 2026-08-30 01:19"），那么每一轮的前缀都不同，**25000 token 全部按原价重付**。

**一句话总结**：稳定放前，易变放后。

### 5.2 压缩前的峰值

很多客户端会在上下文接近窗口上限时才触发压缩/摘要。问题是——**达到峰值那一轮，你已经按最大上下文付过费了**。而且压缩后旧内容丢失，AI 可能开始"忘记"之前的约定，反而诱发你重新解释，进入新一轮消耗。

**应对**：主动管理，别等到被自动压缩。上下文过半时就考虑开新会话 + 带摘要。

### 5.3 失败的循环最贵

一个跑偏的 Agent：

```
迭代 1-8：失败（每次都带着完整历史重发）
迭代 9： 成功
```

账单 = 单次成功成本的 **9 倍**，而且前面 8 次的输出对你毫无价值。

**应对**：**早停 > 重试**。连续失败 2–3 次就停，把问题拆小、描述改精确、换个干净会话重来。这不只是省钱，往往还更快。

### 实验 1：数一次 token，建立实感

**目的**：知道"一份文档到底值多少 token"，从此对上下文有数量级概念。

```bash
python w6_cost_lab.py count --file w6_sample_policy.txt
python w6_cost_lab.py count --file README.md
```

**预期输出**（2026-08-30 在 MAX 上实测）：

```
文件: w6_sample_policy.txt
  字符数:   806
  token 数: 680  [估算]
  参考: 相当于约 0.9 页 A4 纯文本（按每页约 750 token 折算）
  若每次提问都全文塞入，问 50 个问题 = 34,000 token
```

> 装了 tiktoken 时标记会变成 `[tiktoken 精确]`，数字会略有出入（上面这份实测是 680 token，精确计数通常在 500–700 之间）。

**你会学到**：原来区区 806 个字符就有 680 token。**"每次提问都带全文"的成本，是单次成本的 50 倍**——而这还只是一页纸的量。换成 80 页的制度手册，这个倍数会放大到让你肉疼。

### 实验 2：亲手复现"滚雪球"曲线

**目的**：亲眼看到平方增长，这是全文最重要的一条直觉。

```bash
python w6_cost_lab.py snowball --rounds 20 --per-round 2000
```

**预期输出**（示意）：

```
轮次   全量历史(本轮)   累计        窗口策略(本轮)   累计
1      2,000            2,000       2,800            2,800
5      10,000           30,000      10,800           34,000
10     20,000           110,000     10,800           88,000
20     40,000           420,000     10,800           196,000

结论：20 轮后，全量历史累计 420,000 token，窗口策略 196,000 token，节省 53.3%
```

**参数说明**：`--per-round` 是每轮新增的 token（提问+回答+工具结果）；窗口策略默认保留最近 5 轮 + 800 token 摘要，可用 `--window` / `--summary` 调整。

**你会学到**：曲线的形状比数字更重要——**前面平缓，后面陡峭**。这解释了为什么"聊了很久的会话"会突然变得又慢又贵。

### 实验 3：全文塞入 vs Top-k 检索（核心实验，直接服务 W6）

**目的**：量化证明 RAG 的价值。同一批问题，对比两种喂上下文方式的 token 消耗。

```bash
# 用内置评估集（40 题）跑对比
python w6_cost_lab.py ab

# 只跑前 10 题（快速看效果）
python w6_cost_lab.py ab --max-q 10

# 对比不同的 k 值
python w6_cost_lab.py ab --k 1
python w6_cost_lab.py ab --k 3
python w6_cost_lab.py ab --k 5
```

**预期输出**（2026-08-30 实测，全量 40 题）：

```
[检索器] 未找到有效政策文件，回退使用示例数据：w6_sample_policy.txt
```

**目的**：感受不经截断的命令输出有多可怕。

**你会学到**：从此你会本能地给命令加 `| head`、`--tb=short`、`-x`。**截断输出是 Agent 使用者最重要的肌肉记忆之一**。

### 实验 5：图片分辨率对比

**目的**：验证"缩放图片能省 token，且通常不影响答案"。

```bash
# 用项目里已有的示例图片
python w6_cost_lab.py count --image example.jpg
```

**预期输出**（2026-08-30 实测）：

```
图片: example.jpg
  原始尺寸:    1024 x 1024
  缩放后尺寸:  768 x 768
  估算 tile 数: 4      → 约 765 token  [估算]
  若上传前先缩到 512px 宽 (512 x 512):
  估算 tile 数: 1      → 约 255 token  [估算]
  节省: 66.7%
```

**你会学到**：边长减半，token 降到约 1/3——因为是按 tile（面积）计费，**不是按边长线性关系**。所以"先缩放再上传"的收益比直觉更大。问 UI 布局、报错截图这类问题时，512px 通常完全够用。

**踩坑笔记**：图片 token 的估算规则各家模型不同（tile 大小、是否对长边切分都有差异），**这里给的是量级参考，精确值以各家官方定价文档为准**。需要精确计费时，直接看 API 返回的 usage 字段。

### 实验 6：串行 vs 并行

**目的**：理解"时间"这一维度的优化——**并行能省时间，但省不了 token**。

```bash
python w6_cost_lab.py parallel --tasks 5 --sleep 0.3
```

**预期输出**（2026-08-30 实测）：

```
模拟 5 个独立任务，每个耗时 0.30 秒

串行执行: 1.50 秒
并行执行: 0.33 秒   (线程数 5)
加速比:   4.5x

注意: 并行不改变 token 总量 —— 它省的是时间，不是钱。
```

**你会学到**：优化前先分清目标。想省钱就减上下文，想省时间就加并行，**别指望一个手段解决两个问题**。

### （可选）实验 7：看真实 API 的 usage 字段

> **⚠️ 这一步会真实花钱。必须先设预算上限，并用最便宜的模型。**

**目的**：把理论数字和真实账单对上，理解 `prompt_tokens` / `completion_tokens` / `cached_tokens` 的含义。

```python
# 保存为 check_usage.py 后运行
import os
from openai import OpenAI

client = OpenAI(api_key=os.getenv("DEEPSEEK_API_KEY"),
                base_url="https://api.deepseek.com")

resp = client.chat.completions.create(
    model="deepseek-chat",
    messages=[{"role": "user", "content": "用一句话解释什么是 token"}],
    max_tokens=200,          # 硬上限，防止意外长输出
)

u = resp.usage
print(f"输入 token: {u.prompt_tokens}")
print(f"输出 token: {u.completion_tokens}")
print(f"总计:       {u.total_tokens}")
# 若返回体里有缓存相关字段，也会一并打印出来看看
print("完整 usage:", u.model_dump())
```

**预期输出**（示意）：

```
输入 token: 12
输出 token: 47
总计:       59
完整 usage: {'prompt_tokens': 12, 'completion_tokens': 47, 'total_tokens': 59,
             'prompt_cache_hit_tokens': 0, 'prompt_cache_miss_tokens': 12}
```

**踩坑笔记**：
- **必须设 `max_tokens`**，这是防止意外长输出的第一道保险。
- 缓存字段（`prompt_cache_hit_tokens` / `prompt_cache_miss_tokens`）**不是所有厂商都返回**，返回了就重点观察：第二次发相同前缀的请求，hit 数应该明显上升。
- 建议在项目里加一个"预算护栏"（每日/每次会话累计花费上限），超出即停。你的 `w4_chat_module.py` 里的 `BudgetExceeded` 就是干这个的，**保持这个好习惯**。

## 7. 节流速查表（Cheat Sheet）

**省 token（省钱）**

- 检索只取 top-k，绝不全文塞入
- 固定内容（系统提示、项目说明）放最前，易变内容（时间戳、当前问题）放最后 → 命中缓存
- 命令输出一律截断后再回灌
- 长对话定期压缩成摘要，或直接开新会话
- 一个任务完成就开新会话
- 图片先缩放再上传；能贴文本就别贴图
- 小模型做粗筛/分类，大模型只做精判
- 简单任务关掉推理模式
- 索引增量更新，不全量重建

**省时间（省等待）**

- 独立任务明确要求并发执行
- 长输出改为"先大纲，后分段"
- 缩小测试/构建范围
- 优先用有 API 的数据源，少抓需要渲染的网页
- 给所有网络操作设超时
- 控制并发数，避免触发限流退避

**防失控（安全）**

- 每次调用都设 `max_tokens`
- 给 Agent 循环设最大迭代次数
- 设置会话级和日级预算上限，超出即停
- 连续失败 2–3 次就停手，别硬扛
- **绝不用生产环境的 key 裸跑循环脚本**

## 8. 附录 A：Token 量级直觉表

| 对象 | 经验量级 | 记忆锚点 |
|---|---|---|
| 一句中文提问 | 10–30 token | 几乎不要钱 |
| 一页 A4 纯文本 | 500–1,000 token | 一千字左右 |
| 一份 80 页制度手册 | 4–8 万 token | 接近长上下文模型的 1/4 窗口 |
| 一次网页全文抓取 | 5,000–20,000 token | 抓 3 个网页 = 一本书的几章 |
| 1080p 截图 | 1,000–2,000 token | 缩到 768px 可降到 1/4 |
| 一小时会议录音转文字 | 8,000–12,000 token | 约 1 万字 |
| 一个中型 Python 文件（300 行） | 3,000–6,000 token | 读 10 个文件 = 5 万 token |
| 输出一份 5000 字报告 | 6,000+ token 输出 | 输出单价约是输入的 4–5 倍 |

> **重要**：以上均为**经验估算值**，各家模型的 tokenizer 与定价差异明显，**不要直接拿去算成本**。需要精确数字时，用实验 1 的方法实测，或读 API 返回的 usage 字段。

## 9. 附录 B：初学者常见误区 Q&A

**Q：把对话历史清空，AI 是不是就变笨了？**
A：不会变笨，只是"失忆"。正确做法是先让它把关键信息**总结成一段话**，你复制出来贴进新会话。几百 token 换掉几万 token，非常划算。

**Q：是不是应该尽量少给上下文，问得越短越好？**
A：不是。**缺信息导致的答错 + 反复纠正，远比一次性给足信息贵**。原则是"给必要的最小充分信息"——用检索精确给到相关片段，而不是既不给又不给全。

**Q：用了 RAG 就一定省钱吗？**
A：检索本身也有成本（向量方案还要 embedding 费用），但**在文档量大、提问次数多的场景下，节省是压倒性的**。实验 3 会给你具体数字。文档很小（比如就一页）时，直接塞全文反而更简单。

**Q：为什么同样的任务，有时快有时慢？**
A：多半不是模型变慢了，而是：触发了限流在退避等待、工具调用在等外部响应、或者上下文变大导致每轮处理变慢。**先查是不是在排队**。

**Q：缓存命中率怎么看？**
A：看 API 返回的 usage 里的缓存字段（如 `prompt_cache_hit_tokens`）。**注意不是所有厂商都提供这个字段**，DeepSeek 等部分厂商会返回。没有返回时，只能通过费用变化间接判断。

**Q：我是初学者，是不是不用管这些？**
A：恰恰相反。**成本意识越早建立越好**——它不只是省钱，更是理解 Agent 系统如何运作的一把钥匙。等你做 W6 和后面的多 Agent 项目时，会发现"上下文管理"是 Agent 工程的核心命题之一。
