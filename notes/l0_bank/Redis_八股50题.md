# L0 题库 · Redis 50 题

> **用途/格式/口径**：同 network_50.md。**高频重点**：缓存三大问题、持久化 RDB/AOF、数据结构与底层编码、分布式锁、过期与淘汰、集群与一致性。

## 一、数据结构与底层（8 题）

### 1. Redis 为什么快？
- **简答**：纯内存操作、单线程免锁免切换、IO 多路复用、高效数据结构（SDS/跳表/紧凑编码）。
- **深答**：四点展开：①内存随机读 100ns 级 vs 磁盘 ms 级；②命令执行单线程串行——无锁、无上下文切换、时间复杂度可预期；③epoll 事件循环处理万级连接（呼应 OS 题 28）；④针对场景的特化结构：SDS O(1) 取长度、ziplist/listpack 小数据省内存、跳表做范围查询。注意口径：6.0 引入的是**网络 IO 多线程**，命令执行仍是单线程——这是 2026 年面试必纠的错误。
- **来源**：Redis 官方文档（FAQ/How fast is Redis）；《Redis 深度历险》第 2 章

### 2. 五大基本类型与典型场景？
- **简答**：String（缓存/计数）、List（队列/时间线）、Hash（对象）、Set（去重/交并）、ZSet（排行榜/延迟队列）。
- **深答**：每个类型给一个「命令+场景」：INCR 做接口计数与限流；LPUSH+BRPOP 任务队列（但生产用 Streams/专业 MQ）；HSET 存对象部分更新免序列化整对象；SINTER 求共同关注；ZADD score 存时间戳做延迟队列（轮询 ZRANGEBYSCORE）。新类型：Bitmap（签到）、HyperLogLog（UV 估算）、GEO（附近的人）、Stream（消费组日志）。
- **来源**：Redis 官方文档 Data Types；《Redis 深度历险》第 1 章

### 3. SDS 与 C 字符串的区别？
- **简答**：SDS 记长度（O(1) strlen）、预分配减重分配、二进制安全、杜绝缓冲区溢出。
- **深答**：C 字符串以 \0 结尾：strlen O(n)、不能存二进制（\0 截断）、拼接无长度检查。SDS 头部存 len/alloc，空间预分配（<1M 翻倍、>1M 每次加 1M）与惰性释放把多次拼接的 realloc 摊薄。这是「为场景改造数据结构」的经典教学案例。
- **来源**：《Redis 设计与实现》第 2 章；Redis 源码 sds.h（需复核版本）

### 4. 跳表的原理？为什么 ZSet 用跳表不用红黑树？
- **简答**：多层有序链表，查找/插入 O(log n) 概率化实现；比红黑树实现简单、范围查询顺链表走、还支持按排名定位。
- **深答**：每节点随机层数（幂次定律，每层概率 25%），高层是低层的快速索引。vs 红黑树：①范围查询 [100,200] 跳表定位起点后顺链表走，红黑树要中序遍历；②实现与调试简单；③无旋转操作。Redis 跳表还带 span 字段直接算排名（ZRANK O(log n)）。ZSet 同时有 ziplist/listpack（小数据）+skiplist+dict（成员→score 映射，O(1) 查分值）的混合实现。
- **来源**：《Redis 设计与实现》第 5 章；Redis 官方文档（实现说明）

### 5. 什么情况下 ZSet/Hash 会从紧凑编码转成标准编码？
- **简答**：元素个数或单元素长度超过阈值（如 list-max-llist-entries 等）时，ziplist/listpack/intset 转标准结构。
- **深答**：listpack（7.0 替代 ziplist）内存紧凑（连续存储省指针）但插入删除要整块挪动，只适合小规模；超阈值转 skiplist/hashtable 换性能。参数：hash-max-listpack-entries 等。工程含义：小对象用对编码能省 10 倍内存——大 key 治理与内存优化都从这里下手。
- **来源**：Redis 官方文档（Memory optimization）；《Redis 设计与实现》

### 6. Redis 单线程为什么还要考虑并发问题？
- **简答**：命令级原子，但「多命令组合」不原子（INCR 后 EXPIRE 之间可插入）；需要 MULTI/EXEC、Lua、或单个命令搞定。
- **深答**：经典竞态：判断 GET key 是否存在再 SET——两步之间别的客户端可插入。解法梯度：①单命令原子（SET key val EX nx 即原子判断+写）；②MULTI/EXEC 事务（打包执行但不回滚，EXEC 前被 WATCH 打断才放弃——乐观锁）；③Lua 脚本（服务端原子执行整段逻辑，W6 若做限流迁移 Redis 就用 INCR+EXPIRE 的 Lua 保证原子）。这是分布式锁正确性的根。
- **来源**：Redis 官方文档（Transactions/Lua）；《Redis 深度历险》第 2 章

### 7. Stream 与 List 做消息队列的对比？
- **简答**：Stream 有消费组、ACK、Pending 列表、ID 连续性——是「日志+消费组」模型；List 只是无确认队列。
- **深答**：List 的 BRPOP 弹出即丢，消费者崩溃消息就没了；Stream 消息留在日志里，消费组各自维护 last-delivered-id，XACK 才确认，XPENDING 可重投（PEL 列表）。还支持按 ID 回溯（XREAD 从任意位置读）。但 Redis MQ 的定位仍是轻量场景：无分区自治、无严格事务，量大还是要 Kafka/RocketMQ——「知道边界」比「会用」值钱。
- **来源**：Redis 官方文档（Redis Streams Tutorial）

### 8. Bitmap/Bitfield 的场景与内存账？
- **简答**：一亿用户的签到用 Bitmap 每人 1 bit≈12MB/天；SETBIT/BITCOUNT 做 0/1 统计，BITFIELD 做整段计数。
- **深答**：Bitmap 是 String 的位视角：offset 即下标，稀疏 offset 会浪费（一亿用户只活跃 100 人就别用 bitmap，用 Set）。典型：连续签到天数（BITCOUNT 区间）、布隆过滤器（多个 hash 定位多 bit，解决缓存穿透，见题 18）、UV 近似（HyperLogLog 12KB 固定误差 0.81%）。内存敏感场景先算账再用。
- **来源**：Redis 官方文档（Bitmaps/HyperLogLogs）；《Redis 深度历险》

## 二、持久化（6 题）

### 9. RDB 的原理与优缺点？
- **简答**：fork 子进程把内存快照写成二进制文件；恢复快文件小，但两次快照之间的数据会丢、fork 瞬时可能有延迟毛刺。
- **深答**：save 触发时主进程 fork——COW 保证子进程看到一致性快照（呼应 OS 题 14），主进程继续写，写多的实例内存最多近乎翻倍（要监控）。优缺点对称面：AOF 丢数据少但文件大恢复慢。实操：RDB 适合冷备/容灾快照，AOF 承担低 RPO，两者常同时开。
- **来源**：Redis 官方文档（RDB persistence）；呼应 os_50.md 题 14

### 10. AOF 的写回策略与重写机制？
- **简答**：appendfsync always/everysec/no 三档（丢 0/≤1s/窗口不定）；文件大了触发重写，fork 子进程按当前内存生成最小命令集替换旧文件。
- **深答**：everysec 是性能与安全的默认平衡点；no 托管给 OS（呼应 OS 页缓存，丢窗口不可控）。AOF 重写同样 fork+COW，期间写命令同时进 aof_buf 与 aof_rewrite_buf 保证重写期间增量不丢（7.0 后 Multi-Part AOF 重构了该机制，细节需复核版本）。追问点：为什么重写用「内存现状生成命令」而不是「压缩旧命令」——最小且正确。
- **来源**：Redis 官方文档（AOF persistence）；《Redis 设计与实现》第 11 章需复核 7.0 变化

### 11. 混合持久化是什么？
- **简答**：4.0+ 的 aof-use-rdb-preamble：重写时前半段是 RDB 全量、后半段是 AOF 增量——恢复快且丢得少。
- **深答**：纯 AOF 恢复要逐条重放命令（慢）；混合文件前半 RDB 二进制直接载入，只重放后半增量。代价：RDB 前缀可读性差（排查工具不友好）。7.x 默认开启。结论口径：缓存场景 RDB 就够，要低丢失选混合+everysec。
- **来源**：Redis 官方文档（AOF persistence, 4.0+ release notes 需复核）

### 12. fork 与持久化的关系？大实例 fork 慢会怎样？
- **简答**：RDB/重写都要 fork；实例越大 fork 越久（复制页表），期间主进程阻塞，10GB 级可达数百毫秒。
- **深答**：fork 成本≈复制页表（页表 1GB/约 2MB，需复核精确数），加上触发时 TLB/缓存冲击。症状：定时 RDB 时刻延迟毛刺。缓解：控制单实例内存（分片）、低峰执行、关 THP（透明大页反而放大 COW 复制粒度——Redis 启动日志的 WARNING 就是这个）。这是「Redis+OS 知识合并题」的标准答案。
- **来源**：Redis 官方文档（Latency generated by fork）；呼应 os_50.md 题 14

### 13. 恢复优先级与数据丢失边界？
- **简答**：AOF 优先（丢得少）于 RDB；everysec 最坏丢约 1 秒；复制场景还要算主从切换的丢窗口。
- **深答**：启动加载顺序：启用 AOF 用 AOF，否则 RDB。丢失边界公式化：everysec≈1s；主从异步复制下主挂从未同步的数据也会丢——真正低丢失要 wait 命令（同步等待 N 从）或足够 min-replicas-to-write。缓存 vs 存储定位不同容忍度：缓存丢了回源即可，存储定位必须配持久化+多副本。
- **来源**：Redis 官方文档（persistence 总览、WAIT 命令）

### 14. 关闭持久化当纯缓存可以吗？
- **简答**：可以（save "" + 关 AOF），丢失即回源；但要配对策略：启动预热、防止穿透、内存上限。
- **深答**：纯缓存模式的隐性前提：①回源服务扛得住冷启动（Redis 重启即雪崩窗口——预热/分批启动，见题 17）；②淘汰策略正确（allkeys-lru 等）；③监控命中率。反之，如果里面存了「回源代价极高或不可再算」的数据（如积分），就必须持久化+多副本——「数据可再算性」决定持久化策略，这个判断框架比记配置值重要。
- **来源**：Redis 官方文档（persistence）；雪崩防护（题 17）

## 三、过期、淘汰与内存（7 题）

### 15. 过期键的删除策略？
- **简答**：惰性删除（访问时检查）+定期删除（每百毫秒抽样清理），不依赖单一机制。
- **深答**：定期任务每次抽 N 个带过期时间的键，过期比例超 25% 继续抽（有时间上限防阻塞）。注意：不活跃的过期键若没被抽样到，占着内存直到惰性触发或淘汰。相关面试题：过期时间存在哪——独立的过期字典（expires dict），不是改键值。主从的过期由主删除后同步 DEL 给从（从库不主动过期），否则会不一致。
- **来源**：《Redis 设计与实现》第 8 章；Redis 官方文档（How Redis expires keys）

### 16. 八种内存淘汰策略与选型？
- **简答**：noeviction（默认，写报错）、lru/lfu × allkeys/volatile、random × 2、volatile-ttl；缓存场景用 allkeys-lru 或 allkeys-lfu。
- **深答**：volatile 系只淘汰带 TTL 的键——若混存持久数据，过期键不足时等于不淘汰，写报错；allkeys 系全量淘汰。LRU vs LFU：访问高峰把热键冲掉的场景选 LFU（4.0+，计数衰减防历史热点永驻）。maxmemory 必须配（否则吃满内存开始 swap，性能雪崩——呼应 OS 题 38）。多实例混布时按业务隔离实例配策略。
- **来源**：Redis 官方文档（Eviction policy）；《Redis 深度历险》

### 17. 缓存穿透、击穿、雪崩的区别与防护？
- **简答**：穿透=查不存在的数据（防：布隆过滤器/空值缓存）；击穿=热 key 过期瞬间打库（防：互斥重建/逻辑过期）；雪崩=大量 key 同时失效或 Redis 挂（防：过期时间加抖动/多级缓存/限流）。
- **深答**：三者的判定顺序：先问「数据存在吗」（穿透）→「是单个热点吗」（击穿）→「是成片吗」（雪崩）。空值缓存要有短 TTL（否则新数据上线也被挡）；互斥重建用分布式锁或单飞（singleflight，同进程合并并发回源）；雪崩的过期抖动=`ttl + random(0,300s)` 一行代码。这是后端面试出现率最高的 Redis 题，务必能画出请求路径图。
- **来源**：Redis 官方文档（bloom filter 模块需复核）；《Redis 深度历险》；呼应 D4 任务 cache_problems_demo.py（无防护 100 次回源→有防护 1 次）

### 18. 布隆过滤器原理与误判？
- **简答**：多个哈希函数置位判断「一定不存在或可能存在」；有误判率（假阳性），不支持删除（计数布隆除外）。
- **深答**：误判率由位数组大小 m、元素量 n、哈希个数 k 决定（最优 k≈0.7m/n）；装满后误判飙升，要按容量预算建。Redis 4.0+ 用 RedisBloom 模块，或自己用 bitmap+多 hash 模拟。穿透防护的落地姿势：先把全量 key 灌入布隆，查询先过布隆再查缓存/库；新 key 双写。变体：布谷鸟过滤器支持删除。
- **来源**：《Redis 深度历险》；RedisBloom 模块官方文档（需复核版本）

### 19. 什么是大 key 与热 key？怎么治理？
- **简答**：大 key=单键过大（value>10KB 或集合元素过多，拖慢命令与迁移）；热 key=单键 QPS 极高（打满单分片）；治理：拆分、本地缓存、复制多副本+随机后缀。
- **深答**：大 key 危害：DEL 一个百万元素 ZSet 阻塞主线程（用 UNLINK 异步删+SCAN 分批）、迁移卡顿、过期阻塞。发现：redis-cli --bigkeys/--hotkeys、MONITOR 抽样、RDB 离线分析。热 key 治理：应用层本地缓存（一级缓存）、key 加随机后缀分散到多分片再聚合读、读写分离副本。预防优先于事后治理：设计期约定集合大小上限。
- **来源**：Redis 官方文档（keys scan/async delete）；阿里云 Redis 开发规范（需复核链接）

### 20. Redis 的内存碎片怎么处理？
- **简答**：分配器（jemalloc）尺寸类别导致碎片；看 mem_fragmentation_ratio（>1.5 异常）；主动碎片整理 activedefrag 4.0+。
- **深答**：ratio<1 说明用了 swap（严重事故信号，呼应 OS 题 38）；1.1-1.5 正常。activedefrag 借 jemalloc 原地搬移数据，要给 CPU 上限防影响主流程。工程预防：value 尽量同尺寸、避免频繁大改小、用「新建+改名」替代原地改。
- **来源**：Redis 官方文档（Latency due to memory fragmentation/activedefrag）

### 21. 客户端连接数与 timeout 常见坑？
- **简答**：连接要池化复用；空闲 timeout 过短导致「连接被掐」（报 Connection reset），配置 maxclients 与客户端池参数要匹配。
- **深答**：每请求新建连接的开销是 TCP+AUTH+SELECT 三个 RTT，池化是铁律（Jedis/Lettuce/go-redis 都默认池）。TCP keepalive 与 Redis timeout（默认 0 不踢）配合；云 Redis 常有 LB 空闲超时（如 4 分钟），客户端池要设 maxIdle 且加 keepalive 心跳。排查：CLIENT LIST 看连接归属与 idle 时间。
- **来源**：Redis 官方文档（CLIENT/timeout）；各客户端池文档需复核

## 四、主从、哨兵与集群（8 题）

### 22. 主从复制的流程与缓冲区？
- **简答**：从库 psync 带复制偏移量→全量（主 bgsave RDB+期间写命令缓存）或部分重同步（repl_backlog 覆盖则补发增量）。
- **深答**：复制积压缓冲区 repl_backlog（环形）决定断线后能否走增量：偏移量仍在环内→partial resync 免全量。全量同步的隐藏成本：bgsave fork（呼应题 12）+网络传输+从库载入，主从抖动期连环全量同步是事故放大器，backlog 要按「断线时长×写入速率」估算。
- **来源**：Redis 官方文档（Replication topology）；《Redis 深度历险》主从篇

### 23. 哨兵的原理与选主？
- **简答**：多哨兵互检+探测主库，多数派确认主观下线→客观下线→按优先级/偏移量/runid 选新主→通知客户端。
- **深答**：防误判靠仲裁（quorum 与 majority 的区别：确认客观下线要 quorum，执行切换要 majority）。选主规则：slave-priority 高者优先→复制偏移量大（数据最全）→runid 小。客户端不直连主库而是查哨兵（或用支持哨兵协议的驱动）。要点：哨兵本身要奇数多节点部署防脑裂，且不能与主库同生共死（不要全在一台机器）。
- **来源**：Redis 官方文档（Sentinel）；《Redis 深度历险》哨兵篇

### 24. 脑裂与 min-replicas-to-write？
- **简答**：主被隔离期间客户端仍写旧主，恢复后旧主降级清空本地→丢数据；min-replicas-to-write + min-replicas-max-lag 让主在没有足够健康从库时拒绝写。
- **深答**：脑裂的本质是「多数派仲裁与客户端可达性不一致」。哨兵切走后，旧主还活着时的写入全丢。缓解参数正是 Redis 内建的「写多数派」约束，代价是可用性下降（从库全断时主拒写）。任何 CAP 讨论都能落到这个参数上——「Redis 不是 CP 系统」的正确打开方式。
- **来源**：Redis 官方文档（Replication: min-replicas 配置）；Sentinel 文档

### 25. Cluster 的槽位机制与路由？
- **简答**：16384 槽按 CRC16(key)%16384 分给各主节点；客户端可直连任意节点，MOVED/ASK 重定向引导；smart client 缓存槽位映射。
- **深答**：槽=数据分片单位；why 16384——心跳包里槽位图用 bitmap 压缩，1.6KB/实例（作者解释，需复核原文）。key 的 hash tag（{user1000}.follow）可强制同槽支持多 key 操作与 Lua。扩缩容=迁移槽（ migrating/importing 状态+逐 key 迁移）。客户端分类：smart（JedisCluster/Lettuce）vs 代理（Codis/云代理）。
- **来源**：Redis 官方文档（Redis Cluster specification/tutorial）；why-16384 出处需复核

### 26. Cluster 下多 key 命令与事务的限制？
- **简答**：MSET/多 key Lua/事务要求所有 key 同槽（hash tag 解决）；跨槽报 CROSSSLOT 错误。
- **深答**：设计含义：业务要「按实体聚合 key」——如 {user_id}:profile、{user_id}:cart 同槽，用户维度的原子操作可行；全局维度（全局排行榜）要拆方案（各分片算+聚合，或用全局单实例/ZSet 分桶）。这是「分片系统通用矛盾」在 Redis 的具象化——本地事务边界=分片边界，与 mysql 题 43 同构。
- **来源**：Redis 官方文档（Cluster spec：keys hash tags）；呼应 mysql_50.md 题 43

### 27. Redis 集群模式下主从切换的数据一致性预期？
- **简答**：异步复制+多数派切主：主挂时未同步到从的写入会丢；集群是 AP 优先，强一致需求别用 Redis 当唯一存储。
- **深答**：一致性预期公式：RPO≈主从复制延迟（毫秒级但非零）+故障检测窗口（秒级）。业务设计守则：Redis 存「可重算/可回源」的数据；资金/库存的唯一真源在 DB，Redis 只做加速或「超卖保护」的辅助锁（见题 28 的权衡）。这句话是面试「Redis 丢数据怎么办」的定海神针。
- **来源**：Redis 官方文档（Cluster spec: consistency guarantees）

### 28. 分布式锁的正确姿势与 Redlock 争议？
- **简答**：单实例：SET key val NX PX ttl + 唯一值 + Lua 释放（校验 value 防删别人的锁）；要高可用加看门狗续期；Redlock 多实例多数派方案存在争议，强一致需求改用 ZooKeeper/etcd 或 DB 乐观锁。
- **深答**：单实例锁的漏洞：锁过期但业务没执行完→并发进入；解法：续期线程（看门狗，如 Redisson）或把 TTL 设得远大于任务时长+幂等兜底。Redlock 争议（Martin Kleppmann vs antirez，2026 年仍是高频面试题）：时钟漂移与 GC 停顿下多数派锁不保证互斥——结论：互斥是强需求时用共识系统，Redis 锁定位「效率锁」（防重复劳动）而非「正确性锁」（防资损）。W6 若做多实例限流，用 Redis INCR+Lua 而非分布式锁。
- **来源**：Redis 官方文档（Distributed locks）；Martin Kleppmann 博客「How to do distributed locking」（需复核原文）；Redisson 文档

### 29. 主从+哨兵 与 Cluster 怎么选？
- **简答**：数据量小（<25GB）QPS 中等：主从+哨兵简单够用；容量/写吞吐要横向扩展：Cluster；能用客户端分片/代理解决的过渡期也行。
- **深答**：Cluster 的代价清单：多 key/事务/Lua 受限、运维复杂、云上托管的成熟度差异。演进路径建议：单机（读多）→主从+哨兵（高可用）→读写分离副本（读扩容）→Cluster（容量/写扩展）。提前用 hash tag 约束 key 设计可让将来上 Cluster 平滑——「为扩展性预留设计」是架构题的收尾话术。
- **来源**：Redis 官方文档（Cluster tutorial）；各云厂商托管 Redis 文档需复核

### 30. 什么是无 DISCARD 的「事务」缺陷？WATCH 怎么补？
- **简答**：MULTI/EXEC 只保证打包执行，出错不回滚（不支持 rollback）；WATCH 提供乐观锁：被监视 key 变动则 EXEC 放弃。
- **深答**：设计哲学：Redis 事务错误主要是「用法错误」（编译期错误会在 EXEC 前拒绝）而非运行期冲突，回滚意义有限。WATCH+RETRY 实现 CAS：`WATCH stock; GET; 判断; MULTI; SET; EXEC` 失败重试——高竞争下重试风暴，不如 Lua 一把梭。对比 MySQL：Redis 的「事务」是命令打包，不是 ACID 事务——面试纠错点。
- **来源**：Redis 官方文档（Transactions）；呼应 mysql_50.md 题 15-17

## 五、性能与排障（7 题）

### 31. 缓存与数据库一致性方案（Cache-Aside 落地细节）？
- **简答**：先更新 DB 再删缓存；并发窗口残留用延迟双删或订阅 binlog 异步删兜底；能接受最终一致才用缓存。
- **深答**：与 mysql_50 题 50 呼应，Redis 侧补充：删除失败的兜底（消息队列重试）、热点 key 频繁失效的保护（逻辑过期：值里带过期时间，后台异步刷新，前台永不阻塞）、先删后更新的坑（并发读回填旧值）。方案分层：TTL 兜底（所有方案的地板）→ 删除缓存 → binlog 订阅（最终一致且解耦）。
- **来源**：呼应 mysql_50.md 题 50；《Redis 深度历险》；延迟双删出处需复核

### 32. Redis 慢的原因排查清单？
- **简答**：slowlog 看慢命令（KEYS/大集合全量/复杂 Lua）、大 key、fork 毛刺、swap、网络、CPU 争抢、AOF 刷盘阻塞。
- **深答**：系统化排查：①SLOWLOG GET 看命令分布（KEYS/O(n) 命令上线禁用，用 SCAN）；②INFO stats 的 latest_fork_usec（fork 毛刺）；③内存是否 swap（mem_fragmentation_ratio<1）；④持久化阻塞（aof_delayed_fsync 计数）；⑤宿主机其他租户干扰。规律：Redis 的慢 90% 是「使用者用错」，引擎本身极快。
- **来源**：Redis 官方文档（Latency monitoring/Redis latency problems troubleshooting）

### 33. KEYS 为什么危险？SCAN 的原理？
- **简答**：KEYS O(N) 阻塞主线程；SCAN 渐进遍历（游标+桶反转保证不漏，可能重复），生产必用 SCAN。
- **深答**：SCAN 的游标是反向二进制迭代：遍历中 rehash 也能「不漏」（可能多报），客户端要容忍重复（幂等处理）。SCAN COUNT 是每桶扫描数不是总数。hscan/sscan/zscan 同理。运维红线：MONITOR 生产禁用（全量命令流）、KEYS/FLUSHALL 走审批+rename 成空命令。
- **来源**：Redis 官方文档（Keys scan）；《Redis 设计与实现》

### 34. pipeline 与 MULTI 的区别？
- **简答**：pipeline 是客户端攒批一次发（省 RTT，不保证原子）；MULTI/EXEC 是服务端打包（保证原子）；两者可叠加。
- **深答**：网络往返才是批量场景的真正成本（万次 set 的 RTT 远超执行时间）。pipeline 的注意点：攒批过大撑爆客户端缓冲与网络，分批（如 500/批）并等待响应；原子性需求再上 Lua。W6 的 MCP 场景类比：并发工具调用（dispatch.gather）就是在应用层做「批量化+并发化」。
- **来源**：Redis 官方文档（Pipelining）；呼应 W6 dispatch.py 设计

### 35. Lua 脚本的使用边界？
- **简答**：脚本原子执行适合「读-判断-写」组合；但要短小（阻塞主线程）、只用 KEYS/ARGV（集群 hash tag 友好）、幂等可重试。
- **深答**：经典脚本：限流（INCR+EXPIRE 原子）、库存扣减、分布式锁释放（GET 比对+DEL）。风险：脚本里的循环/大集合操作会阻塞整个实例（呼应单线程模型）；脚本超时（busy-loop）会触发 SCRIPT KILL 的尴尬窗口。7.0 的 Functions 是脚本的组织化进化。原则：「Lua 是原子性的工具，不是业务逻辑的家」。
- **来源**：Redis 官方文档（EVAL/Functions）；《Redis 深度历险》

### 36. Redis 6.0 多线程线程模型到底改了什么？
- **简答**：多线程只用于网络读写与协议解析，命令执行仍单线程——并发安全模型不变，收益在大包大连接场景。
- **深答**：动机：万兆网卡下单线程网络 IO 成了瓶颈（内核 syscall+拷贝跟不上）。io-threads 4-6 即可，太多反而调度开销。含义：你的竞态分析与 Lua 依赖完全不受影响——「改性能不改语义」的工程典范。面试纠错：说「Redis 6 之后命令执行多线程」直接扣分。
- **来源**：Redis 官方博客（Redis 6.0 release notes 需复核）；Redis 官方文档（Threading）

### 37. 客户端缓存的原理？
- **简答**：6.0 的 client-side caching：客户端本地存热 key，服务端失效时经 RESP3 推送 invalidation 消息。
- **深答**：两种模式：默认（跟踪所有访问的 key，自动失效广播）与 broadcasting（订阅前缀，客户端自滤）。收益：省一次 RTT 与服务端负载；成本：客户端内存与失效风暴（热 key 抖动）。适用：读极多改动少的字典类数据（配置/权限）。与多级缓存（本地→Redis→DB）的思想链一致：越靠近计算越快，越要管理一致性。
- **来源**：Redis 官方文档（Client-side caching）

## 六、应用场景设计（7 题）

### 38. 用 Redis 实现延迟队列？
- **简答**：ZSet score=执行时间戳，生产 ZADD，消费侧轮询 ZRANGEBYSCORE time now 取到期任务，处理完 ZREM（Lua 保证原子防多消费者重复）。
- **深答**：要点：①取与删必须原子（Lua）否则多消费者重复消费；②取到未确认就崩溃会丢任务——PEL 模式（参考 Stream）或先 ZADD 到「处理中」队列；③轮询间隔与延迟敏感度的权衡，空轮询用阻塞化变体或监听通知。适用边界：任务量中小、秒级精度；重任务/高吞吐上专业 MQ（延迟消息）。
- **来源**：Redis 官方文档（ZSet/Lua 组合，需复核 tutorial）；《Redis 深度历险》延迟队列篇

### 39. 用 Redis 做排行榜/排行榜的并发更新？
- **简答**：ZSet 天然排行榜：ZINCRBY 更新、ZREVRANGE 取榜、ZREVRANK 查名次；并列名次用 score 拼时间戳细分。
- **深答**：细节：①同分排序规则：score=分数*1e6+(1e6-时间戳) 之类编码，先到先排前；②超大榜（千万级）ZREVRANGE 分页 OK 但全量导出昂贵；③防刷：更新前限流（INCR 次数）+黑名单 Set。变体：多维度榜（日/周榜）用 key 带日期滚动+过期清理。
- **来源**：Redis 官方文档（ZSet 命令）；《Redis 深度历险》

### 40. 用 Redis 做接口限流？与 W6 的关系？
- **简答**：固定窗口 INCR+EXPIRE、滑动窗口 ZSet 存时间戳、令牌桶 Lua；W6 v1.7 单机内存版限流，多 worker 部署时正要迁到这套 Redis 方案。
- **深答**：三种实现取舍：固定窗口有临界突刺（窗口边界双倍）；滑动窗口 ZREMRANGEBYSCORE+ZCARD 精确但 ZSet 大了慢；令牌桶 Lua 平滑支持突发。分布式前提：所有实例对同一 Redis 计数——这正是 W6 rate_limit.py 注释「生产多副本换 Redis」的落地路径，面试可直接引用自己的代码演进思路（单机内存→Redis 集中计数）。
- **来源**：W6 w6_hr_policy/app/rate_limit.py 注释；Redis 官方文档（Lua 限流模式需复核）；呼应 network_50.md 题 43

### 41. Session 共享怎么用 Redis 做？
- **简答**：会话对象序列化存 Redis（key=session_id，EXPIRE=会话时长），无状态服务节点都读同一 Redis，水平扩展免粘性。
- **深答**：细节：①过期用 Redis TTL 替代自维护定时刷新（每次访问 EXPIRE 续期）；②大 Session 拆 Hash 部分更新；③敏感数据加密或不入 Session；④高可用等级与登录态的重要性匹配（哨兵起步）。与 JWT 的取舍呼应 network_50 题 22：要「可主动踢人」就 Session+Redis，要「服务端零状态」就 JWT。
- **来源**：Spring Session 官方文档（模式参考需复核）；呼应 network_50.md 题 22

### 42. 什么是「缓存预热」与上线发布流程？
- **简答**：新缓存上线/重启后，提前把热数据批量灌入（SCAN 源库或热点清单），避免冷启动雪崩。
- **深答**：预热来源优先级：流量统计的热点清单（最准）>全量小表>定时任务扫描。灌入注意 pipeline 批量+限速（别把 Redis/源库打挂）；发布配合：实例滚动重启（一部分保服务）、预热完成再切流量。W6 上线（v1.7）对应的预热对象是 policy_context 的 BM25 索引（进程内，重启即建，秒级）——「预热什么取决于重建成本」。
- **来源**：实践通用（各大厂缓存规范需复核）；呼应 network_50.md 题 14

### 43. Redis 实现分布式 Session 之外的「全局计数器」？并发正确性？
- **简答**：INCR 原子自增是全局唯一 ID 的简易方案；要批量取号用 INCRBY 减少往返；严格趋势递增+分片用号段/雪花。
- **深答**：INCR 计数器的可用性风险：Redis 不可用则发号停摆（缓存场景可容忍，ID 场景致命）。工程演进：Redis 号段（一次取 1 万个内存发）→ DB 号段双 buffer → 雪花（本机自足）。并发正确性核心：INCR 单命令原子（呼应题 6），无需 Lua。这是「把 Redis 用在哪一层」的判断题。
- **来源**：Redis 官方文档（INCR）；Leaf/雪花方案需复核

### 44. 用 Redis 做签到与统计（Bitmap 实战）？
- **简答**：SETBIT uid offset=天数，BITCOUNT 统计月签到天数，BITOP OR 合并多月，BITPOS 找首次签到。
- **深答**：细节：offset 上限规划（一年 365 位/用户），稀疏用户（注册晚）offset 从「注册日偏移」算省空间；BITCOUNT 的 start/end 是字节不是位（易错）；亿级用户月维度 12MB 是合理账。UV 场景换 HyperLogLog（允许 0.81% 误差、固定 12KB）。数字敏感场景先做内存预算表。
- **来源**：Redis 官方文档（Bitmaps）；《Redis 深度历险》Bitmap 篇

### 45. 「附近的人」怎么实现？
- **简答**：GEO（底层 ZSet+geohash 编码）：GEOADD 存位置、GEOSEARCH 半径查询、GEODIST 算距离。
- **深答**：geohash 把二维经纬度一维化（相邻格子前缀相近，但边界不连续——查 9 邻格补全）。规模上限：单 ZSet 千万级位置可行（内存预算），更大要按城市分 key。原理追问：geohash 的 base32 串前缀相似≈地理相近，但存在边界突变（位于分界两侧的近邻 hash 差很远）——所以查询要扩展邻域。变体方案：MySQL 空间索引/R 树、ES geo_query，按数据量与查询模式选。
- **来源**：Redis 官方文档（Geo commands）；geohash 原理（维基/需复核）

## 七、综合（5 题）

### 46. Redis 与 Memcached 的区别与选型？
- **简答**：Redis 丰富数据结构+持久化+复制+Lua+集群；Memcached 纯 KV 多线程、内存利用率高、超大简单缓存场景仍有席位。
- **深答**：选型口径：需要结构化操作/持久化/高可用→Redis；纯扁平 KV、超大内存池、多线程抗热点→Memcached 有历史优势（但现在 Redis 分片也普遍）。现实：新项目默认 Redis。答出「两者内存分配器差异（slab vs jemalloc）」属于加分深水区。
- **来源**：Redis 官方 FAQ；Memcached 官方 wiki（需复核）

### 47. Redis 会被什么替代？2026 视角的新趋势？
- **简答**：没有被替代，但边界被重新划分：持久内存级产品（如 Dragonfly 多线程兼容 Redis 协议）、云厂商 Serverless KV、专用向量库承接 AI 场景。
- **深答**：诚实口径（避免编造具体份额）：①Redis 生态仍是事实标准，兼容协议的新引擎（多线程、C++ 重写）在特定负载下性能更强；②AI 应用浪潮下「Redis 作为向量库（RediSearch 向量索引）」与专用向量库的取舍是新面试题；③Serverless 化按量计费改变容量规划方式。回答策略：承认变化、给出判断依据（负载特征/成本/生态），不背份额数字。
- **来源**：Redis 官方文档（向量搜索需复核）；Dragonfly 官方文档（需复核）；行业报告需复核——标「需核实」不引数字

### 48. 如何给 Redis 做容量规划？
- **简答**：估算内存（键数×平均 value+编码开销+碎片 20%）→maxmemory 留 30% 余量→副本/集群倍乘→QPS 估算选规格。
- **深答**：方法模板：①key 数量与 TTL 分布清单；②value 尺寸分布（P99）；③编码选择影响（listpack vs hashtable 差 5-10 倍，题 5）；④峰值 QPS×命令平均成本→CPU 规格（单分片命令执行单线程，QPS 上限≈10 万级需复核）；⑤增长曲线与扩容预案（Cluster 分片数预取 2 倍）。输出物是「容量表格」而不是拍脑袋数字——这题考工程习惯。
- **来源**：Redis 官方文档（Memory optimization）；云厂商容量计算器需复核

### 49. Redis 的监控指标与告警阈值？
- **简答**：核心指标：命中率、内存（maxmemory 占比/碎片率）、连接数、慢日志增量、主从延迟、fork 耗时、AOF 阻塞计数。
- **深答**：阈值经验：命中率<90%（缓存定位）查穿透/失效策略；碎片率>1.5 或 <1 告警（<1 即 swap，事故级）；主从延迟>1s 告警；latest_fork_usec 毛刺关联抖动投诉。工具链：INFO 全量采集（redis_exporter+Prometheus）、慢日志抓取、关键命令审计（rename KEYS）。告警要分层：容量类提前预警、可用性类立即响应。
- **来源**：Redis 官方文档（INFO）；redis_exporter（GitHub，需复核）

### 50. 结合 W6 项目，Redis/缓存知识会落在哪里？
- **简答**：三个落点：限流器从单机内存升级 Redis 集中计数（多 worker 部署）、政策问答结果缓存（同问题 TTL 内直返，省 DeepSeek 调用）、将来公网后的防刷（IP 计数+黑名单）。
- **深答**：可展开的设计叙述：①限流：rate_limit.py 注释已预留「生产换 Redis」，用 ZSet 滑动窗口+Lua（题 40）；②问答缓存：以「规范化问题文本 hash」为 key 缓存答案，注意政策文档更新时的失效（版本号进 key）；③防刷：INCR 每 IP 请求 + SETNX 临时封禁——与 W6 fail-closed 鉴权组成纵深防御。答法示范同 OS 题 50：机制→项目证据→踩坑。
- **来源**：W6 w6_hr_policy/app/rate_limit.py；W6 v1.7 部署规划（B4 任务）
