# 08 · ReAct vs Plan-and-Execute

> 来源：冲刺版 §5.1 第二梯队-8｜ 配套：C4_working_modes.md 模式 2/3

## 30 秒答
ReAct「边想边干」：每步基于最新观察决策，灵活但 token 消耗大；Plan-and-Execute「先想好再干」：一次性产出完整计划再逐步执行，省 token 但计划错了系统性返工，需要 re-plan 兜底。**任务不确定性越高越偏 ReAct，确定性越高越能 Plan-and-Execute**。

## 2 分钟深答
- **为什么 W6 选 ReAct**：问答任务的依赖是动态的——「先检索条款才知道要不要算年假、算完可能还要查发放规则」，前置计划大概率作废；实测 trace 也证明 ReAct 的每步决策都依赖上一步观察（检索结果里的章节号决定下一步）；
- **Plan-and-Execute 的甜点**：步骤结构化（爬取→分析→报告）、计划可人工审核、批量处理同类任务时计划可复用——省掉每步的「思考」调用；
- **Token 账**：ReAct 每轮都带全部历史 messages；Plan-and-Execute 思考一次后执行阶段可以只带当前步骤——长任务里差距显著；
- **工程常态是混合**：先 plan 出骨架，执行中发现偏差允许局部 re-plan（LangGraph 的图编排即此模式的框架化，我们 2027Q1 P3 引入时终止/重规划逻辑可映射为条件边）。

## 追问预案
- 「ReAct 每轮全量历史，上下文爆了怎么办？」→ 我们的对策是上下文预算闸门：token 估算超 70% 触发 compact（早期对话压成 150 字摘要，保留最近 4 轮原文）——context.py 实装。
- 「怎么评测两种模式？」→ 同一评测集分别跑，比 score2+成本+步数分布；这也是「评测体系先行」的价值。
