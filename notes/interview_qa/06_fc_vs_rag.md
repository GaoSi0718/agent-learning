# 06 · Function Calling 和 RAG 的区别与选用

> 来源：冲刺版 §5.1 第二梯队-6

## 30 秒答
FC 是「让模型调能力」（动作出口），RAG 是「给模型供知识」（事实入口）。不互斥：W6 的 search_policy 本身就是「RAG 之上的 FC 封装」——用 FC 的机制去触发一次 RAG 检索。一句话：**FC 是手，RAG 是料**。

## 2 分钟深答
- **选用时机**：需要「外部事实/知识」→ RAG；需要「执行动作/取实时数据」→ FC（或两者结合）；
- **W6 实例**：年假问题三步——FC 调 search_policy（内部是 BM25 检索=RAG）→ FC 调 calc_annual_leave（计算能力，RAG 给不了）→ 综合作答。知识库问答场景里 FC 和 RAG 是配合关系不是二选一；
- **边界案例**：模型参数内的常识（「解释什么是 SSE」）两者都不需要——直接回答，且我们的 system prompt 要求它如实说明「这不在政策问答职责内」（12 轮记忆测试 R02 实测行为）；
- **选型证据**：技能要求层面 FC/RAG 在 JD 里同现（复旦类脑院：RAG+Agent 开发经验；蔚来：RAG/智能对话/Agent/知识库）——工程上两者是同一个「工具+知识」栈的两面。

## 追问预案
- 「RAG 也能『回答』，为什么还要 FC？」→ RAG 只补上下文，不能「做事」：算不出工龄天数、查不了某天是否工作日——动作必须经 FC 落到确定性代码。
- 「FC 调 RAG 会不会多余？」→ 封装成工具反而好：检索的参数（query/category）、失败行为（回传「未检索到」）都被 schema 约束，模型用它比「自由发挥拼接上下文」可控得多。
