# 11 · MCP 是什么、解决什么问题、与 Function Call / A2A 的关系

> 来源：冲刺版 §5.1 第二梯队-11｜ 引入排期：P3（2027.03，D1 决策）——如实说「计划引入」

## 30 秒答
MCP（Model Context Protocol）是「模型↔工具/数据源」的开放协议：工具方按协议实现一次（MCP Server），任何支持 MCP 的客户端（Host）都能发现并调用——**一次封装，处处可用**。类比 USB-C。与 Function Call 的关系：FC 是「模型表达调用意图」的模型侧机制，MCP 是「工具如何被发现、鉴权、跨进程调用」的生态侧标准；A2A 则是 Agent 之间互操作的标准。

## 2 分钟深答
- **解决什么**：M×N 集成问题——没有协议时 M 个模型框架对接 N 个工具要写 M×N 份胶水；MCP 把它变成 M+N（各自实现一次协议）；
- **与 FC 的分工**：模型仍然用 FC 语义「决定调什么」；MCP 决定「工具从哪来、怎么连」——我们 W6 的工具注册表（tools.py 的 TOOLS+IMPL）是**进程内单机版**，MCP 相当于把它服务化+标准化的路径（注册表→协议 Server）；
- **能力面**：tools 之外还有 resources（数据源暴露）与 prompts（模板）——把「知识」也标准化暴露；
- **安全视角（加分）**：MCP Server 是第三方代码/进程——这正呼应 Agent 安全面：恶意 MCP server 是 CVE-2025-53773 攻击面的一部分（见 17 题），所以「工具白名单+确定性校验门」在 MCP 时代更重要而不是过时；
- **诚实边界**：我们尚未接入 MCP（P3 排期），以上是基于规范的理解 + 项目内等价物（注册表）的映射——不装用过。

## 追问预案
- 「为什么现在不用？」→ 单机单进程场景引入协议层是负资产；等 B4 公网部署后，第三方扩展工具的需求出现时再切——和「不提前上框架」同一决策框架。
- 「MCP 和 OpenAPI/插件有什么区别？」→ 交互协议面向「模型可用性」设计（发现/描述/调用的一致语义），且双向流式；传统 OpenAPI 面向人类开发者阅读。
