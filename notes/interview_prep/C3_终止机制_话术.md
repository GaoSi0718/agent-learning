## 1. 三机制的代码事实（先背熟证据再背话术）

**代码证据** `w6_hr_policy/app/agent_loop.py:11-39` `LoopBreaker`：

```python
def __init__(self, max_steps=MAX_STEPS, repeat_limit=3,
             step_timeout=API_TIMEOUT, total_timeout=120):
    self.max_steps = max_steps
    self.repeat_limit = repeat_limit
    self.step_timeout = step_timeout
    self.total_timeout = total_timeout
    self.history = deque(maxlen=repeat_limit)
    self.start = time.time()
```

**check() 的三个判定**（agent_loop.py:28-39）：

| # | 机制 | 判定（行号） | 防什么 |
|---|---|---|---|
| 1 | **max_steps** | `if step >= self.max_steps: return True, f"max_steps({self.max_steps}) reached"`（:30-31） | 步数上限兜底——无论 LLM 多能折腾，8 步必停（MAX_STEPS 从 `.env` 读，配置化） |
| 2 | **repeated_action** | 动作指纹 = md5(工具名+规范化参数)，存 `deque(maxlen=3)`；`len(set(history))==1` 即连续 3 次同动作 → break（:34-38，reason=`repeated_action(search_policy) x3`） | 「换个说法反复干同一件事」的隐蔽死循环——不是重复调用才停，是**同参数重复** |
| 3 | **双层超时** | 单步 `API_TIMEOUT`（.env 配置，传入 LLM 调用）+ 总闸 `total_timeout=120s`（:32-33） | 单次调用挂死 + 累计耗时失控 |

**执行顺序的关键设计**（agent_loop.py:55-67）：三件套检查在**执行工具之前**——同一批次里第 3 次重复动作直接中断，「注定中断的批次不浪费执行」，钱不白花。中断也给用户交代：返回 `（已中断：repeated_action(...)）根据已有信息：…`，**绝不静默失败**（:67）。

**实测证据**：`tests/test_c2_loop_breaker.py` 死循环用例 3 步停止，trace 记录 `{"step": 3, "type": "break", "reason": "repeated_action(search_policy) x3"}`——「可复盘」是终止设计的另一半：**每次中断都有 reason 留在轨迹里**。

## 2. 三档话术

### 30 秒版（电梯/一面快问）

> "三层防线：步数上限兜底、重复动作检测、双层超时。我的实现里每次调工具前先算「工具名+参数」的指纹，连续三次一样就断——因为换个措辞反复检索同一个词是最典型的死循环。而且检查发生在执行之前，注定中断的批次不浪费一次 API 调用；每次中断都带 reason 写进 trace，事后可复盘。有测试用例：构造死循环输入，验证第 3 步精确停止。"

### 2 分钟版（标准深挖）

> "我把终止拆成三个正交机制，对应三种失控模式：
> **第一，步数上限**。MAX_STEPS=8 从环境变量读，这是兜底——不管模型怎么幻觉，8 步内必停。它是资源预算的硬闸。
> **第二，重复动作检测**。光数步数不够：真实死循环往往是「换个说法重复同一动作」，比如连续三次用同一关键词检索。我对每次调用算「工具名+规范化参数」的 MD5 指纹，放在一个长度为 3 的滑动窗口里，窗口内全相同就触发 break。选 3 不选 2：给模型一次「重试后自己修正」的机会，第二次重复才确认是死循环。
> **第三，双层超时**。单步超时控制一次 LLM 调用（默认 30 秒，可配置），总闸 120 秒控制整轮 Agent——单步预算乘以重试次数加上退避时间必须小于总闸，这个算术我们在可靠性层做过：3 次 × 30 秒 + 1.5 秒退避 ≈ 91.5 秒，低于 120 秒，重试不会击穿总闸。
> 两个设计细节我认为最重要：一是**先检查后执行**——终止判定放在工具执行之前，注定中断的批次一次执行都不浪费；二是**中断可复盘**——break 时返回带 reason 的消息给用户、同时写进 trace，绝不静默失败。这套东西有测试：死循环用例第 3 步精确停止，reason 是 repeated_action(search_policy) x3。"

### 5 分钟版（深水区，含权衡与追问应对）

> 在 2 分钟版基础上追加三层：

> **"为什么指纹用参数规范化？** 因为同一语义的调用可能参数有微小差异——我们用 JSON 序列化 sort_keys 后再哈希，保证「语义相同」的调用指纹相同。这里有个已知权衡：如果模型连续两次用略有不同的关键词检索同一主题，语义上是重复的但指纹不同，当前检测抓不到——这是 precision/recall 的取舍，我们宁可漏检（多花一两次调用）也不误杀（中断正常的多轮探索）。P1 评测跑满步数用例时可以校准这个阈值。
>
> **超时为什么做成两层？** 单步超时是「这一步挂了就放弃这一步」，总闸是「整轮 Agent 的资源预算」。只设单步的后果：模型每步都成功但走 100 步，总耗时照样失控；只设总闸的后果：一次网络挂死占满整个预算。两层交集才等于「可控」。
>
> **为什么中断了还要返回内容？** 终止三件套的输出不是异常是「降级答案」：`（已中断：reason）根据已有信息：{LLM 已有内容}`。用户视角下 Agent 挂着不返回是最差的体验，把已有结论+中断原因交代出去，产品上才闭环。这和我们在可靠性层的降级（LLM 全挂时返回检索原文）是同一原则：**任何失败路径都必须以内容收尾，绝不静默**。
>
> **这套机制和框架比差在哪？** LangGraph 这类框架把终止条件做成图上的条件边与检查点，能持久化恢复；我们 P0 手写的版本只保证「当轮可控」，没有断点续跑。这是有意的取舍——先吃透机制再上框架，2027Q1 引入 LangGraph 时终止逻辑可以直接映射成图的条件边。"

## 3. 追问预案（面试官下一层会问什么）

| 追问 | 答法要点 |
|---|---|
| 为什么是 3 次重复，不是 2 次？ | 给一次自愈机会（LLM 拿到错误回传后常自己换参数）；2 次误杀率升高，5 次浪费预算。3 是实测的平衡点，且窗口 `deque(maxlen=3)` 让检测 O(1) |
| 指纹碰撞怎么办？ | MD5 在单进程内的「工具名+参数」空间碰撞概率可忽略；真要较真可换 sha1/记录原文——这是成本收益问题不是技术问题 |
| MAX_STEPS 设多大合适？ | 按任务拓扑估：W6 的问答任务 1 次检索+1 次计算+1 次收尾≈3-4 步，8 步留 2 倍余量；上限值本质是「预算×单价」的财务决策，所以放 .env 不硬编码 |
| 检查在执行前，会不会把合法的第三步误杀？ | 会——但合法场景下第 3 步与前两次完全同参的概率极低（参数里有 query 差异）；宁可误杀也保证「失控场景 0 浪费」，这是安全侧偏置 |
| 怎么验证这套机制真的工作？ | `tests/test_c2_loop_breaker.py`：构造必然死循环的 FakeLLM（永远返回同一调用），断言第 3 步 break 且 reason 正确——**测试替身可控地制造故障，这是离线测试的核心价值**（与 400 bug 的教训互补：逻辑类故障用桩，协议类故障用端到端） |

## 4. 与其他考点的连线

- **与 B3 可靠性**：终止三件套管「Agent 层失控」，resilience.py 管「单次 LLM 调用层失控」（重试/降级）——两层超时预算的算术（91.5s < 120s）是它们必须对齐的接口；
- **与 C1**：重复动作检测依赖「工具名+参数」——这正是 dispatch 双重校验里同一批字段，两个机制共享同一套动作表示；
- **与 D5/成本**：「10 步 95% 成功率 → 整体 59.9%」的算术（0.95^10）说明为什么步数上限直接决定端到端可靠性——步数是复利公式里的指数。
