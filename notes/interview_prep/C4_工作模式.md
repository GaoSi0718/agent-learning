## 第一部分 · 四种工作模式（对照自己代码讲）

### 模式 1：纯 Prompt 链（Prompt Chaining / Workflow）

**定义**：固定步骤编排，LLM 只在预设节点被调用，无自主决策。LLM 只是「流程里的函数」。
**代码对照**：W6 若把「检索→拼 prompt→回答」写死成顺序调用就是纯链。对照 `agent_loop.py:45-47` 的 messages 组装——如果去掉循环、去掉 tool_calls 分支，只跑一次 chat，就是链式。
**什么时候够用**：步骤固定、无需分支判断的场景（ETL 式摘要、固定模板改写）。**优势**：可预测、便宜、易测；**劣势**：无法处理「不知道哪一步会失败」的开放任务。
**面试一句话**：Workflow 是「人定流程，LLM 执行节点」；Agent 是「LLM 定下一步，代码执行」。

### 模式 2：ReAct（推理-行动循环）——W6 的当前模式

**定义**：LLM 每轮输出「思考 + 行动（工具调用）」，程序执行后把结果喂回，循环到 LLM 给出最终答案。
**代码对照**：`agent_loop.py:49-53` 的主循环——

```python
for step in range(1, breaker.max_steps + 1):
    resp = llm.chat(messages, tools=tools, timeout=breaker.step_timeout)
    if not resp.tool_calls:
        trace.append({"step": step, "type": "final", "content": resp.content})
        return resp.content, trace
```

没有 tool_calls = 模型决定「行动阶段结束」——**终止权在模型，资源权在代码**（终止三件套，见 C3）。工具执行结果以 tool message 回传（agent_loop.py:90-95），构成 ReAct 的「行动→观察」闭环。
**实测证据**：B2 端到端「工龄 12 年年假」问题，trace 两步：`step1 search_policy(ok, 14ms)` → `step2 final（带章节 6.4.6 出处）`——这正是 ReAct「先查再答」的标准轨迹。
**防死循环**：C3 的三件套（max_steps=8 / repeated_action×3 / 双层超时 120s）。

### 模式 3：Plan-and-Execute

**定义**：先让 LLM 产出完整计划（步骤列表），再逐步执行（可带重规划）。与 ReAct 的区别：**计划先于行动**，行动阶段只执行不再思考。
**W6 为什么没选它**：问答任务的依赖是动态的——「先查条款才知道要不要算年假、算完可能还要查发放规则」，前置计划大概率返工；ReAct 每步基于最新观察决策，更适合探索型任务。
**什么时候选它**：步骤高度结构化（如「先爬 A 再分析 B 最后写报告」）、需要人审计划的场景；代价：计划错误会系统性传导，需要 re-plan 机制兜底。
**面试一句话**：ReAct 是「边走边看」，Plan-and-Execute 是「先看地图再出发」；任务不确定性越高越偏 ReAct，确定性越高越能省 token 用 Plan-and-Execute。

### 模式 4：多智能体协作（Multi-Agent）

**定义**：多个各自带工具/人设的 Agent 通过消息/交接协作（如 LangGraph 的 supervisor/worker 图）。
**W6 的现状（如实说）**：**没有多智能体**——v1.6 是单 Agent + 3 工具。按 D1 决策，多智能体与框架延后到 P3（2027.03）引入，当前阶段不硬蹭。
**但能讲清设计预留**：`dispatch.run_calls` 的「调用即数据」（`{"name","status","result","latency_ms"}` 收敛结构，dispatch.py:37-46）让「工具调用」与「子 Agent 调用」可以同构处理——把 one() 里的 IMPL[name](**args) 换成子 Agent 的 run_agent，就是 supervisor 模式的雏形。**架构上留了门，工程上没过度建设**——这是对「为什么不先上多 Agent」最有力的回答。
**反问素材**：面试官若问「多 Agent 的坑」：通信语义（传什么上下文）、错误隔离（一个子 Agent 死循环烧谁的预算）、评测（整体成功率 vs 单 Agent 贡献）。
