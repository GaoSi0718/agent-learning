# 五段式 Bug 故事集（bug_stories）

> **用途**：冲刺版 §5.3「每个项目准备 2–3 个真实 bug 故事」。五段式各 30 秒内：①场景 → ②根因 → ③排查路径（最显素养）→ ④修复取舍 → ⑤复盘沉淀。
> **纪律**：全部真实发生（有代码/测试/commit 佐证）；排查路径要讲「排除了哪些假设」；复盘要落到「沉淀了什么规则」。

---

## 故事 1 · 评估指标 regex 捕获组 bug（0.025 假象）

- **① 场景**：跑官方评测脚本，40 题关键词命中率均值 0.025——几乎全零，但人工抽看答案明明包含关键词。
- **② 根因**：`_KEY_PAT` 的捕获组写法 `(\.\d+)?`——`re.findall` 有捕获组时只返回**组内容**而非整体匹配，于是绝大多数题的「关键词列表」变成空/残缺，被 `if kws else 0.0` 强制 0 分；唯一幸存的是含小数 0.5 的题（捕获组非空）。
- **③ 排查路径**：先怀疑语料/检索（换 k 值无效）→ 再逐题打印分数分布，发现「只有含小数的题非零」→ 反推正则行为，用最小例子验证 findall+捕获组语义 → 定位。
- **④ 修复取舍**：改非捕获组 `(?:\.\d+)?` 或 findall 换 finditer 取 group(0)——选前者（改动最小、语义最直白）。
- **⑤ 复盘**：修复后真实命中 0.41/0.47，同时暴露评测集与语料错位——**一个假象挖出两层问题**。沉淀规则：「指标可信度先于分数」「评分代码本身要有最小单测」。

## 故事 2 · tool 回传协议 400（FakeLLM 自测全绿，真实调用即崩）

- **① 场景**：B2 端到端实测，Agent 第一步检索成功，第二步把工具结果回传后 DeepSeek 直接 HTTP 400。
- **② 根因**：OpenAI 协议要求——回传 tool 结果前必须先把发起调用的 assistant **原始消息**入栈，且每条 tool 消息带 `tool_call_id`；两者缺一即 400。清单源码两处都缺。
- **③ 排查路径**：读 400 响应体定位到消息序列 → 对照官方协议要求逐条核对 messages 结构 → 发现 tool 消息「悬空」（前面没有对应的 assistant.tool_calls 消息）。
- **④ 修复取舍**：`_Resp` 增加 `.raw` 保留原始 assistant 消息（llm.py）+ 回传时补 tool_call_id（agent_loop.py）。取舍点：也可以自己重新拼 assistant 消息，但**原始消息保真**最不易引入新协议偏差。
- **⑤ 复盘**：测试替身的保真度决定它能暴露哪类 bug——逻辑类故障用桩（快/免费/可控），协议类故障必须端到端。修复固化成 test_b2_e2e.py 常驻用例。

## 故事 3 · 12 轮记忆测试第 1 轮丢失（load limit 设计缺陷）

- **① 场景**：跨距记忆测试要求第 12 轮答出第 1 轮的「工龄 12 年」，实测必然答不出。
- **② 根因**：load limit=20 行（10 轮）——每轮 user+assistant 共 2 行，第 1 轮在第 12 轮前**必然**滑出窗口；这不是 bug 是设计缺陷：体量控制不该靠「截断历史」承担。
- **③ 排查路径**：先怀疑 SQLite 没存上（查表：48 行都在）→ 再怀疑上下文组装丢消息（打印 messages 长度）→ 最后算窗口数学：10 轮 × 2 行 = 20 行，第 1 轮在第 11 轮开始就被挤出。
- **④ 修复取舍**：limit 20→40（保证跨距）+ 依赖 build_context 的 70% 预算闸门做体量控制。取舍点：无限加大 limit 会顶爆上下文预算，必须两条腿（窗口+压缩）。
- **⑤ 复盘**：容量参数要用「最坏场景数学」验证而不是默认值；12 轮跨距成为回归测试常驻用例。

## 故事 4 · 候选池「无数字外推」幻觉逃过数字校验（R8 迭代实录）

- **① 场景**：Z4 候选池人工抽检发现一道题：源块只有目录行（「内容板块：企业介绍、考勤管理…」），答案却讲「迟到需提供证明、不视为旷工」——编造细节，但**没有一个数字**，数字反幻觉校验直接放行。
- **② 根因**：反幻觉校验只覆盖「数字维度」，对「无数字编造」无感；且目录块被 BM25 召回进年休假补包池，源头就没拦住。
- **③ 排查路径**：`--report-cov` 实测 108 题覆盖率分布 → 发现清晰双峰（编造 ≤0.10 / 忠实转述 ≥0.42）→ 阈值 0.35 落在两峰之间，先验证再定参。
- **④ 修复取舍**：答案-源块 bigram 覆盖率过滤 + 补包池按类别关键词硬门槛（治根因）；阈值做成 `--cov-thresh` 参数并记录校准依据。取舍点：0.55 首版误杀大量忠实转述（加班 16→5），校准后才对——**先测量再定阈值**。
- **⑤ 复盘**：规则一「数字校验 ≠ 忠实性」；规则二「过滤器的阈值必须用分布数据校准」；成本代价：25 次无效补包调用，教训写进 Z4 报告。

## 故事 5 · 受管解释器「目录名 3.13.12 实为 3.13.14」（Z1 实测）

- **① 场景**：Z1 重建 venv 后验收要求「python -V 输出 3.13.12」，实测输出 3.13.14——重建明明成功，判据却「失败」。
- **② 根因**：受管解释器目录名与二进制版本不符（曾原地升级补丁版）；G1 判据把「目录名」当成了「版本承诺」。
- **③ 排查路径**：先怀疑 venv 复制错解释器（检查 venv/pyvenv.cfg 指向）→ 直接对受管解释器本体 `-V`，同样报 3.13.14 → 遍历 versions 目录确认只有这一个版本 → 结论：上游环境事实，非重建问题。
- **④ 修复取舍**：如实记录 + 判据建议改「≥3.13.12」（脚本默认按建议执行，`--strict-venv` 保留字面判据）——**不为了过验收改输出**。
- **⑤ 复盘**：「目录名=版本号」的隐含假设必须实测；G1 自动检查脚本第一晚就揪出这类判据-现实偏差（Z8 的 8绿2红构成变化）。

## 使用法

- 每场面试按岗位挑 2 个：AI 岗首选故事 1+2（评测素养+协议深度）；工程岗首选故事 3+4（容量数学+校准方法论）；
- 讲的时候打开对应文件佐证（agent_loop.py:69-80 / context.py / tools/gen_eval_candidates.py）——「代码在手，故事落地」。
