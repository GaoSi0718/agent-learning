# W6 简历追问压力测试集（w6_grill）

> **用途**：简历 AI 轨上每个数字/表述，预演面试官的三层追问（确认 → 深挖 → 逼边界）与答法要点。
> **使用法**：定稿前自测一遍（每条 3 问都答得出才保留该数字）；面试前一晚只过本文件的「答法要点」列。
> **口径**：全部与 metrics_log 对齐（score2=0.674 / 关键词 0.75 / n=31）；「答不出就删数字」是底线规则。

---

## ① 「score2 复合指标 0.674（关键词口径 0.75）」

- **L1 确认**：0.674 是什么指标？——score2 = 0.6×bigram 召回 + 0.4×数字召回（有数字题时），31 题对齐评测集，k=6；关键词口径 0.75。**不使用「准确率」一词**。
- **L2 深挖**：测试集怎么建的？——原始 40 题写于语料 0 字节时，大面积错位；对齐后 31 题保留/改写（参考答案逐条挂语料章节号），9 题显式 deferred。
- **L3 逼边界**：n=31 够吗？——不够下统计显著性结论；Wilson 95% CI 半宽约 ±13.7pp（40 题口径），如实报告为基线记录；80 条扩充已在做（候选池 84 行待迪莫复核转正）。
- 答不出的兜底话术：「这是工程基线不是研究结论，我按『可复算、可溯源』的标准维护它。」

## ② 「薪酬社保类命中率 0.234 → 0.65」

- **L1**：这两个数怎么来的？——同一评测集前后两次评测的分类得分（k6 score2 口径）；
- **L2**：提升归因给谁？——两项检索优化：标题挂载分块（消标题空壳块）+ 查询侧同义词扩展（「标准工时」→「工时 作息」）；扩展只加查询 token 不改打分；
- **L3**：为什么不继续调到更高？——k=10 时 fact_recall 0.834 但引入跨公司噪声；分类别看，年休假 0.56 是真实短板（双公司双源混淆），是明确的下一步而非借口。

## ③ 「标题挂载分块，323 → 151 chunks」

- **L1**：什么是标题空壳块？——形如「### 6.3.1 工时时间」的短标题行单独成块，占召回名次却无内容；
- **L2**：怎么修的？——短行（≤40 字）并入其后第一个正文段；超长段落滑窗 320/60；
- **L3**：为什么 320？——政策条款段落粒度经验值+召回实测；换语料要重新验证（诚实：参数可调，证据在评测报告）。

## ④ 「3 个 0.5s 任务并发墙钟 0.51s」

- **L1**：怎么测的？——test_b2_dispatch.py 用例 3：asyncio.gather 并发三个 sleep(0.5) 桩工具，perf_counter 计墙钟；
- **L2**：为什么是 0.51 不是 0.50？——事件循环调度与计时精度；判据是 <1.0s（明显非串行 1.5s）；
- **L3**：为什么用协程不用线程？——IO 密集+高并发连接场景 asyncio 开销更低；CPU 密集是另一结论（gil_demo 实测：4 进程 0.96s vs 4 线程 2.39s）——两种场景都能给实测数。

## ⑤ 「12 轮跨距记忆实测通过」

- **L1**：跨距怎么定义？——第 1 轮声明的事实（工龄 12 年）在第 12 轮被正确引用；
- **L2**：架构？——SQLite 按会话存 user/assistant 双方，load 最近 40 行（每轮 2 行），组装时超 70% 预算触发 compact；
- **L3**：踩过什么坑？——初版 load limit=20 行时第 1 轮在第 12 轮前必然滑出窗口——「跨距记忆无从谈起」；改 40 行+compact 是修 bug 不是拍脑袋（main.py 注释留痕）。

## ⑥ 「40 题全量评测成本 <$0.01」

- **L1**：怎么算的？——单题约 $0.0001（输入=片段+prompt，输出=答案，按 DeepSeek 官价），40 题+三次迭代全流程 <$0.015；
- **L2**：怎么控制住的？——RAG 结构决定每次只带 top-k 片段；预算护栏+独立会话；复算/归因全部离线零 token；
- **L3**：这个成本口径可信吗？——API 后台账单可查（2026-09-06 实测）——所有成本数字都可对账。

## ⑦ 「发现并修复评估指标 regex bug（0.025 假象）」

- **L1**：现象？——官方均值 0.025，唯一非零题含小数 0.5；
- **L2**：根因？——`_KEY_PAT` 捕获组 `(\.\d+)?` 让 findall 只返回组内容，39/40 题 `if kws else 0.0` 强制 0 分；修复=改非捕获组或取 group(0)；
- **L3**：这件事的教训？——「指标可信度先于分数」：修复后真实命中率 0.41/0.47（40 题），又暴露出评测集本身的错位——**一个假象下面挖出两层问题**；这也是我们把评测集对齐+归因做成独立工作的原因。

## ⑧ 「协议 400 bug：FakeLLM 自测全绿，真实调用即崩」

- 答法 = C1 §3 的 60 秒模板（assistant 原始消息入栈 + tool_call_id 配对）；
- **L3 逼问**：「说明你的测试体系有漏洞？」——是的：测试替身的保真度决定它能暴露哪类 bug；逻辑类故障用桩、协议类故障必须端到端——修复后已固化 test_b2_e2e.py。**承认盲区+给出分层测试观**，比掩饰加分。

## ⑨ 「API Key 鉴权 + 每 IP 限流」

- **L1**：为什么 fail-closed？——漏配的后果应是「不可用」而非「裸奔」，安全侧偏置；
- **L2**：为什么常量时间比对？——字符串 == 逐字符短路，长度的时序差异可被统计攻击；secrets.compare_digest 常量时间；
- **L3**：多实例怎么办？——内存版单进程计数，多副本迁 Redis 集中计数（ZSet+Lua 原子）——设计边界如实交代。

## ⑩ 「不用任何 Agent 框架」

- 三层答法见 interview_qa/09（封装黑盒/版本地狱/过度抽象 + LangGraph 迁移预案 + 评测让迁移可验证）；
- **红线**：不贬低框架，不吹手写——「先吃透机制再上框架」的排期逻辑。

## 通用纪律（冲刺版 §5.3 全文口径）

- **每个指标五问**：测试集怎么建 / 公式是什么 / 样本量多少 / 是否显著 / 怎么复算——答不出五问的数字不上简历；
- **每个 bug 故事五段式**：场景 → 根因 → 排查路径（最显素养）→ 修复取舍 → 复盘沉淀；
- **规模红线（D9）**：47KB 语料、151 chunks、31 题评测集、本地可用级——绝不「生产级/千条级」。
